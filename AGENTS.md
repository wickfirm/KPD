# AGENTS.md

KPD (Kasumigaseki Properties Development) — Next.js 15 website + ground-up custom CMS. The CMS is feature-complete and in client acceptance testing; the public design is the delivered static site (`public/legacy`) ported to React. **Read `HANDOVER.md` for the current state, working setup, decisions and open items.** See README.md for the contract-scope map.

## Commands

```bash
npm install            # postinstall runs `prisma generate` automatically
npm run dev            # http://localhost:3000
npm run build          # prisma generate && next build
npm start              # production server (after build)
npm run lint           # ESLint 9 (flat config, eslint-config-next ^15.5)
npm test               # Vitest — unit tests for lib/ pure logic
npm run db:push        # Prisma schema sync — uses DIRECT_URL (see DB gotchas)
npm run db:seed        # tsx prisma/seed.ts — idempotent articles/projects/pages
npm run db:studio      # Prisma Studio
```

- `npm run lint` uses `eslint-config-next@^15.5.0` — **do not bump it to v16** (flat-only; crashes under FlatCompat). 3 rules with pre-existing debt are set to `warn` (documented in `eslint.config.mjs`).
- Verification = `npm run build` + `tsc --noEmit` + `npm test` + looking at the real page. When refactoring rendered markup, compare the rendered `<main>` of local and production; for SEO, read each page's head. `compare-render.mjs` diffs old-vs-new rendered DOM for pixel-fidelity regressions (captures in %TEMP%). `node markup-parity.mjs <base-url>` compares the client's delivered HTML in `public/legacy` with a running site (elements, class names, stylesheets, body classes); run it after any change to public markup.

## Environment & DB gotchas

- `.env.local` is gitignored; the repo only ships `.env.example`. Copy it, fill `DATABASE_URL`, `DIRECT_URL`, `AUTH_SECRET`.
- **Two connection strings, non-interchangeable**:
  - `DATABASE_URL` — Supabase Transaction pooler (port **6543**, `?pgbouncer=true`). Used at runtime.
  - `DIRECT_URL` — direct (port **5432**). Used by `prisma db:push` / migrations. `schema.prisma` wires it via `directUrl`.
  - To migrate/seed production in one shot, override `DATABASE_URL` with the direct URL: `DATABASE_URL="<direct url>" npm run db:push`.
- `AUTH_SECRET` must be ≥ 16 chars or `session.ts` throws at runtime.
- `prisma/supabase-init.sql` is a hand-maintained idempotent bootstrap (schema + seed) for pasting into the Supabase SQL Editor — an alternative to `db:push`+`db:seed`. Keep it in sync when the schema changes. Schema changes are additive only and go with a hand-written SQL file in `prisma/` (`add-translations.sql` is the pattern: safe to re-run, and checked with `prisma migrate diff --from-url … --to-schema-datamodel prisma/schema.prisma --script` printing nothing).
- First login to `/admin/login` bootstraps an ADMIN from `ADMIN_EMAIL`/`ADMIN_PASSWORD` **only when the users table is empty**.
- **Do not start a local server with the real `DATABASE_URL` when the local password may be wrong.** A failed authentication is reported as `Can't reach database server`, every page load makes several attempts, and the pooler then refuses new connections for a while (`FATAL: … too many authentication failures, new connections are temporarily blocked`). To compare rendered pages without the shared database, serve the build with `DATABASE_URL` pointed at a dead local address (`postgresql://nouser:nopass@127.0.0.1:1/postgres`), or at a private local PostgreSQL started from the installed PostgreSQL programs on another port (schema with `prisma db push`, then `npm run db:seed` and `npx tsx scripts/refresh-legacy-modules.ts`), deleted afterwards. Found 2026-11-26; details in `HANDOVER.md` §1.

## Architecture & control flow

- **Public pages are React ports of the delivered design** (pixel-identical, DOM-diff verified): `/`, `/about`, `/legacy`, `/developments/*` render CMS content as React components (`src/components/public/*-page.tsx`) inside a **delivered shell** — `src/lib/legacy-*.ts` now only *extract* the shell (header/menu/booking/footer verbatim, links routed, asset paths rewritten to `/legacy/assets/`). Canonical delivered copy lives in `src/lib/*-defaults.ts` (single source of truth shared with admin editors). Delivered `site.js` is re-attached per page via `*-page-scripts.tsx` components (innerHTML scripts never execute). Everything under `public/legacy/**` is still served verbatim. **`public/legacy/assets/css/site.css` must stay byte-for-byte as delivered (no BOM, LF); it is currently the client's 2026-10-05 version (`?v=20261005-mortgage-alignment`), which includes his mortgage-calculator rules**: CMS-era calculator styles live in `ownership-planner-top.css` (loaded before it) and `ownership-planner-end.css` (loaded after it), both imported by `src/app/(public)/public.css` in that order so the cascade is unchanged. Put new CMS-only CSS in `public.css` or a new file, never in `site.css`. This is enforced: `scripts/check-delivered-css.mjs` (the `prebuild` step, and `src/lib/delivered-css.test.ts`) fails if `site.css` differs from the hash in `scripts/delivered-css.sha256`; if the client ever supplies a new stylesheet, replace the file and update the hash with `node scripts/check-delivered-css.mjs --print-hash`. **The Investor page's calculator is the client's own** (2026-10-14, from https://kpd.kmere.com/invest-in-dubai.html): his markup is `src/lib/mortgage-calculator-html.ts` (verbatim; rendered by `invest-view.tsx` inside a `<section {...mortgageCalculatorSectionProps}>`), his script is `public/legacy/assets/js/mortgage-calculator.js` (verbatim), and `mortgage-calculator.test.ts` checks that every id / data-attribute the script uses exists in the markup. Its eligibility form posts to `mailto:`, which `site-cms.js` redirects to `/api/contact` (inquiry type read from the form's hidden "Inquiry Type"). Fees and rates live in his script, not the CMS. The old Ownership Cost Planner (`ownership-cost-planner.js`, CMS Calculator editor) now only appears on development pages. To update: replace those three files with the client's new versions. Figtree is also served from `/legacy/assets/fonts` (`figtree-local.css`) so pages do not fall back to Arial when Google Fonts is blocked. `tsconfig.json` excludes `public/legacy`.
- **CMS lives at `/admin`**:
  - `src/middleware.ts` guards everything under `/admin` (except `/admin/login`) using the edge-safe JWT cookie `kpd_session` (jose HS256, 7-day TTL). The middleware does NOT check the user still exists in the DB; server components/actions re-verify via `requireSession()` (`src/lib/auth.ts`), which redirects to login.
  - Authenticated area is a route group `src/app/admin/(dashboard)/` with a shared layout that renders nav, shows the session user, and defines an inline `logout` server action.
  - **Roles and permissions** (`src/lib/permissions.ts`, single source of truth): ADMIN, EDITOR, CONTRIBUTOR, VIEWER. Every server action starts with `requirePermission("<permission>")` (`src/lib/auth.ts`), which re-reads the user's role from the database, so a role change applies immediately; the middleware only fast-rejects screens by the role in the cookie (`canViewPath`). Contributors are limited to drafts (`mayEditContent`/`allowedStatus`). When adding an action, pick its permission there; do not use bare `requireUser()` for a write. New roles need `prisma/add-roles.sql` run once in Supabase.
  - **Unsaved-changes previews**: editors post their form to a `preview*Draft` server action, which stores a throw-away `site_settings` row (`preview:*`, 2 h expiry) read only by the session-guarded `/admin/preview/*` routes. Page markup lives in shared view components (`HomeView`, `InvestView`, `page-views.tsx`, `ArticleView`, `LegalPageView`, `DevelopmentView`) so the public page and its preview are the same code; the form-to-content builders are shared with the real saves so they cannot drift.
  - **Admin navigation feel**: `(dashboard)/loading.tsx` shows a bar and skeleton instantly; `requireUser()` is `cache()`d per request.
- **SEO / AEO**: all page metadata goes through `pageMetadata()` in `src/lib/seo.ts` (titles <= 60, descriptions <= 160, canonical, Open Graph/Twitter with a default card); fixed-page copy is in `pageSeo` / `legalSeo`; JSON-LD helpers and `<JsonLd/>` live beside it. `/llms.txt` is built from the same data. Never set a bare `openGraph` in a page: it replaces the root one. Editors can override a page's, development's or article's search title/description from the "Search appearance" box; overrides are `site_settings` rows `seo:<page|project|article>:<slug|id>` (`src/lib/seo-overrides.ts`, `src/lib/seo-store.ts`), saved by `saveSeoFor()` in the admin actions and applied in each page's `generateMetadata`.
- **Languages — English, Arabic, Japanese** (state and decisions: `HANDOVER.md` §12). English keeps its unprefixed URLs; `/ar/…` and `/ja/…` are the same routes in another language.
  - **Routing:** `src/middleware.ts` strips the prefix, rewrites to the English route and sets the `x-kpd-locale` request header (an admin preview passes `?lang=ar|ja`). Server components call `getLocale()` (`src/lib/locale.ts`); client components receive `locale` as a prop; data loaders and `pageMetadata()` take it as an argument.
  - **Public code:** every internal link goes through `localeHref(path, locale)` (`src/lib/locales.ts`) — hard-coded links, URLs saved in the CMS (CTAs, cards) and blocks of raw HTML (`localizeHtmlLinks`) alike — and every piece of site-owned text (navigation, breadcrumbs, labels, messages) through `t(locale, "area.name")` (`src/lib/i18n/`: `en.ts` is the source, `ar.ts`/`ja.ts` fall back to it, keys follow the translation sheet). Both return English exactly as given.
  - **Publishing:** one `site_settings` row, key `locales`, e.g. `{"ar":true,"ja":true,"switcher":false}`. A language is reachable only when its switch is on (both are off until turned on); anything else under `/ar` or `/ja` is a 404. The root layout checks this (`getPublishedLocales`).
  - **Switcher:** `src/components/public/language-switcher.tsx` is offered only when the same row also has `"switcher": true` (`getSwitcherLocales`); it switches with a full page load on purpose (a soft navigation between `/about` and `/ar/about` would leave `<html lang>` and `dir` stale). So a language can be switched on, to be reviewed at its address, while visitors see no selector. While the switcher is off, the pages of such a language carry `noindex` (root layout `generateMetadata`), so half-finished translations are not indexed; turning the switcher on makes them indexable.
  - **Fonts and stylesheets:** the Arabic and Japanese faces (`public/fonts/`, sources in its README) and typography rules (`public/locales/ar.css`, `ja.css`) are static files loaded only by pages in that language. Never import them into a bundle.
  - **Invariant:** English pages are identical to what they were, HTML and stylesheets, whether or not another language is reachable and whether or not anything is translated. Keep it that way: compare against `main` before and after any change here. The English editors' markup stays what it was too (apart from the row of language tabs).
  - **CMS translations** (`src/lib/translations/`): a translation lives beside the English it translates, never in it — `article_translations`, `page_translations`, `project_translations` (a null field shows the English text), `project_modules.translations` (`{ ar: { title, content }, ja: … }`) and `site_settings` rows `home:ar`, `global:ar`, `sxs:ar`, `news_listing:ar`, `project-chrome:<id>:ar`, `seo:<kind>:<id>:ar`. A row holds **only the text that differs from English** (`translationDiff`); `mergeLocale` lays it back over the English value, objects by key and lists by position, so a blank or missing field falls back to English. Only keys in `TEXT_KEYS` (`merge-locale.ts`) can ever be translated — images, links, switches, order and styles are shared with English by construction — and `merge-locale.test.ts` fails on a stored key that is not classified as one or the other. **English never reads a translation row** and never selects `project_modules.translations` (queries name `sharedModuleFields`, `src/lib/project-modules.ts`), so the site keeps rendering whether or not the database has had `prisma/add-translations.sql` (run it before merging a change here).
  - **Editor tabs:** `?lang=ar|ja` on an editor is the same form with the translation in it. `useTranslationMode` (`src/components/admin/translation-mode.tsx`) only changes attributes of that form and carries the English form along as hidden `en__*` fields, so the save compares like with like; the English tab's markup is untouched (React derives control ids from the elements around them, so an extra element there — even an empty one — would change them). A translation saves through its own `save*Translation` action, built with the same form builders as the English save, and cannot write an English row. A page's translation is filed by the position of its **saved** blocks (`alignToSaved`), because an editor cannot show every saved block. Versions keep their language (`content_versions.locale`): each language has its own history, and restoring an old Arabic version writes the Arabic row again. The Arabic and Japanese tabs of the **legal** pages are a form over the client's fixed English document (`legal-translation-form.tsx`).
  - **Right-to-left layout** (`public/locales/rtl.css` — generated, never edit it): `node scripts/build-rtl-css.mjs` writes again every rule of the public stylesheets that sets a side, mirrored (`site.css` stays byte-for-byte as delivered), then appends `scripts/rtl-manual.css`, the hand-written part. The root layout links the file on Arabic pages only, after every other stylesheet. Each rule goes through `:where()`, so it keeps the weight of the rule it mirrors and wins only by coming last: whatever out-ranks a rule in English (a more specific rule, a rule for phones, a rule written further down) still out-ranks it in Arabic. A rule that sets a side is written again even when it has nothing to mirror (`margin: 0`), and that set is closed — `top` and `bottom`, `margin-top`, one border side included — or a repeated `inset: 0` beat a later `top: auto` (the legal pages' title ended up behind the header). Run the script after any change to `site.css`, `public.css`, `redesign-pages.css`, `sxs.css` or the two planner sheets; `rtl-css.test.ts` fails when the file is out of date or holds a rule not limited to `html[dir="rtl"]`. Photos, background images and sprites are not mirrored: put an exception in `rtl-manual.css` and say what you saw. An arrow in a React component goes through `arrowGlyph(locale, "→")` (`src/lib/locales.ts`), so it points the way the page reads. `RtlLatinText` (root layout, Arabic pages only) marks text that holds no Arabic letter: such an element follows its own first letter, so an English line keeps its full stop, and a bare number reads left to right; anything with Arabic in it is left alone.
  - **Forms in another language:** a choice reads in the visitor's language and posts the English entry at the same position of its list — never the translated label. The choice lists (`salesProjects`, `customerProjects`, `customerNatures`, `popupInterests`, `interestOptions`) are text keys: a translator edits them on a language's tab, one entry to a line, and a translation also replaces a list the page only has as a built-in default. A form on another language's page sends `visitorLanguage` and its own address; `/api/contact` reads the language from either and gives a non-English submission one more entry in its details, `Visitor language`, which travels to the Messages screen, the team's email and the Salesforce description. **No Salesforce field was added** (ask before adding one). English submissions and the endpoint's English refusals are word for word what they were (`src/lib/submission-language.ts`). Messages go through `formMessage(locale, english, key, fallback)` (`src/lib/i18n/index.ts`): the English text as written on an English page, the sheet's translation elsewhere, and where the sheet has no row for that message the sheet's wording for the same situation. The enquiry pop-up is built by the delivered `site-cms.js` and then reworded by `inquiry-form-copy.js` — its title, button and note from Site settings, its field hints and its choices too. Both look each word up in `window.__KPD_CONTACT.text`, and the pop-up's choices come from `window.__KPD_CONTACT.interestChoices`, each with the English it posts and the text shown (`src/lib/form-words.ts`, published by the footer on Arabic and Japanese pages only; `form-words.test.ts` checks that the table covers every `say("…")` in both scripts, and that the second sets no hint of its own) — an English page publishes none and the scripts show their own. A new fixed string of a form goes in `en.ts` under `form.` or `popup.`, with the sheet's key where a row exists; strings the sheet lacks are listed for the translators in `docs/translations/strings-not-in-sheet.csv`.
  - **Search:** `languageAlternates` (`src/lib/seo.ts`) with `pageLanguages` (`src/lib/hreflang.ts`) declare a page's hreflang alternates only where it has a translation in a language the language selector offers: until the selector is switched on nothing is declared, in a page's head or in the sitemap, because those pages are `noindex` until then (the user's decision of 27 Nov 2026; `src/lib/hreflang-languages.test.ts` keeps the head, the sitemap and the robots tag on the selector). An English page with none declares nothing and is byte for byte what it was; once it has one it declares `en`, each translated language and `x-default` (English), and the sitemap lists the same pages in their language with the same alternates. **A page awaits what its metadata reads.** Next does not hold a page back for its metadata, and one that resolves after the page is streamed to the end of the HTML instead of into its head — seen on production on cold starts, on English article pages too. `pageLanguages` is one read a request (`pageLanguagesOf`, React's `cache`); an article's or a development's whole search appearance is read once for its metadata and its page (`searchAppearance`, in the page file); every page whose metadata reads the database awaits that read itself, and `src/lib/metadata-order.test.ts` fails if one stops doing so. Never add a database read to a `generateMetadata` without the page awaiting the same read. The one page whose head changes order on an un-translated database is the news page (its three preconnect hints now come before the title: same tags, no effect).
  - **The translation importer** (`npm run translations:import -- <options>`; the reading and the matching are in `src/lib/translations/import-sheet.ts`, tested): loads the client's workbook (`KPD-translations-AR-JA.xlsx`, tab "Translations"), which the script reads itself — a spreadsheet is a zip of XML — so it needs no dependency. **A row is placed by its English, never by its Key alone**: the Key is a hint. A row goes at the hinted place if the English there is the row's, otherwise at the one place in the page's English content that holds exactly that text; not found, or found in more than one place, it is listed in the report and left out. Rows of the site's own words (a "(code)" area: `nav.`, `footer.`, `form.`, `brochure.`, `dev.`, `news.`) go to the dictionaries; rows of the client's calculator (`calc.`, `planner.`) are held back. **It never changes an English value**: only a language's own row is written, through the editor's own rule (`translationDiff`). Rows are held back while their Status is not "Approved"; `--allow-drafts` loads them (the brief allows it, by agreement, while the language switch is off). It only reports unless asked to write: `--sql <file>` writes SQL for the Supabase SQL Editor (the usual way on production), `--write --yes` writes into the database `DATABASE_URL` points at, `--dictionaries` regenerates `ar.ts` and `ja.ts` from every file given: the committed files come from the workbook **and** `docs/translations/strings-not-in-sheet.csv`, so pass both (with the workbook alone it refuses, since strings would be lost). A line of a list in the sheet carries the bullet the page draws itself: the importer takes it off the line and off its translation. The legal pages are matched against the fixed document they show (`terms-defaults.ts`), the homepage and the landing page against their effective English (built-in wording with what is saved). `--sheet` may be given more than once, and a file may be a CSV with the workbook's columns: the lists for translators in `docs/translations/` are CSV files, and come back the same way. `--dictionaries` needs every file: it refuses to write while any string that is translated now would have no row.

## Data model (prisma/schema.prisma)

- All camelCase fields map to snake_case tables via `@@map`. All enums are Postgres enums (`UserRole`, `ArticleKind`, `ContentStatus`, `ProjectProfile`, `ModuleKind`, `RssItemStatus`, `SubmissionStatus`). Use `db:push` after edits.
- JSON columns are the flexible-content workhorse: `Article.body` = `string[]` of paragraphs; `ProjectModule.content` = freeform object; `StaticPage.content` = ordered blocks. Translation rows (`*Translation` models, `locale: "ar"|"ja"`, `@@unique([parentId, locale])`) hold only the text that differs from the English on the parent row; a null field shows the English. The CMS writes them from its Arabic and Japanese tabs; the translation importer will fill them from the client's sheet.
- `Article.sourceRssItemId` links an article back to the RSS item that produced it (`@unique` → one-to-one).

## Conventions & style

- **Styling is hand-written CSS.** Public pages: `src/app/globals.css` and the delivered `public/legacy/assets/css/site.css` (+ `src/app/(public)/public.css`). Admin: `src/app/admin/admin.css`, which declares its design tokens in a Tailwind v4 `@theme` block but is styled with `cms-*` classes; append new rules in labelled blocks at the end. `postcss.config.mjs` is intentionally empty and `next.config.mjs` pins `outputFileTracingRoot` so Next does not pick up a parent-folder Tailwind config. The admin palette is deliberately neutral (black / white / off-white) to match the front-end; keep status colours semantic only.
- Path alias `@/*` → `./src/*`.
- Codebase conventions to match: `///` doc comments, box-drawing `──` section dividers in lib files, `export type XxxFormState = { error?: string }` for action state, local `slugify()` helper (defined per-file in `actions.ts`, not shared).
- `package.json` uses a nonstandard `allowScripts` map (npm allow-scripts tooling) — keep it in sync when dependency versions bump.

## Gotchas

- `publishedAt` is set to `new Date()` whenever an article is saved with status PUBLISHED (even a re-save of an already-published article rewrites the date).
- Slug collisions surface as raw Prisma "Unique" errors — map them to friendly messages (existing pattern in `saveArticle`).
- Article body accepts blank-line-separated plain text OR a JSON array of strings (`parseBody` in admin actions).
- Headings that his HTML breaks over two lines (homepage intro/developments/contact headings, a development's Headline, a section title, page hero headings) are `<textarea>`s: a line break becomes `<br>` on the page (`multiline()` in the views). Never make such a field a single-line `<input>` (browsers drop the newline from its value). `normalizeLineBreaks()` (`src/lib/line-breaks.ts`) tidies the text on save.
- RSS slugs are generated as `rss-<timestamp>-...` — safe from collision for RSS-created articles.
- Google News/GDELT parsing is regex/string based and will break silently on feed format changes; wrap new sources in the same Promise.allSettled pattern in `ingestFeeds`.
- The seed uses `upsert(... update: {} ...)` — safe to re-run, but existing rows (incl. `publishedAt`) are never touched.
